# FlatBuffers поверх TCP

Пара выполняет ту же задачу, что `plain-text` и `gRPC`: сервер хранит общий атомарный `uint64`, начиная с 0, и на каждый `Request{id}` отвечает `Response{id, data}` с новым значением счётчика. Один клиент использует одно TCP-соединение.

Запуск из каталога `FlatBuffers` в двух терминалах:

```sh
go run ./cmd/server -listen :9002
go run ./cmd/client 127.0.0.1 9002
```

Каждый запрос и ответ — отдельное FlatBuffers-сообщение с четырёхбайтовым префиксом длины. Схемы находятся в `schema/request.fbs` и `schema/response.fbs`. Клиент накапливает запросы в буфере около 64 КБ, отправляет буфер одним `Write` и одновременно читает ответы. Сервер повторно использует FlatBuffers builder и пишет ответы пачками. При обрыве клиент подключается снова, сохраняя счётчик ID. Настройки TCP не меняются.

Клиент раз в секунду печатает `sent/s`, `responses/s` и общее число ответов. `sent/s` считает выданные ID и может включать текущий вызов `Write`; `responses/s` считает полученные ответы и служит показателем RPS.

Сгенерированный Go-код включён в репозиторий. Для повторной генерации нужен `flatc` версии 25.12.19; Go-библиотека FlatBuffers закреплена в `go.mod`:

```sh
./generate.sh
go test -race ./...
```

В локальном прогоне с одним установленным TCP-соединением (`ss`) и буфером запросов 64 КБ среднее за последние пять секунд составило 8,15 млн ответов/с. В предыдущем прогоне этого же варианта получалось 8,65 млн ответов/с. Результат зависит от машины и нагрузки.
