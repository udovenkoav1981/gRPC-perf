# FlatBuffers поверх TCP

Пара выполняет ту же задачу, что `plain-text` и `gRPC`: сервер хранит общий атомарный `uint64`, начиная с 0, и на каждый `Request{id}` отвечает `Response{id, data}` с новым значением счётчика. Один клиент использует одно TCP-соединение.

Запуск из каталога `FlatBuffers` в двух терминалах:

```sh
go run ./cmd/server -listen :9002
go run ./cmd/client 127.0.0.1 9002
```

Каждый запрос и ответ — отдельное FlatBuffers-сообщение с четырёхбайтовым префиксом длины. Схемы находятся в `schema/request.fbs` и `schema/response.fbs`. Генератор клиента сериализует каждый запрос в повторно используемый массив байт и помещает готовый кадр в ограниченную очередь. Горутина записи ждёт первый кадр, затем забирает все доступные без ожидания и сбрасывает буфер при опустевшей очереди. Буфер также сбрасывается при заполнении до 64 КБ. Если перед сбросом накопилось меньше 1000 байт, горутина один раз уступает выполнение, чтобы принять новые кадры. После копирования кадра в буфер записи его память возвращается в пул. Сервер повторно использует FlatBuffers builder и пишет ответы пачками. При обрыве клиент подключается снова, сохраняя счётчик ID. Настройки TCP не меняются.

Клиент раз в секунду печатает `sent/s`, `responses/s` и общее число ответов. `sent/s` считает выданные ID, включая сериализуемые и ожидающие в очереди запросы; `responses/s` считает полученные ответы и служит показателем RPS.

Сгенерированный Go-код включён в репозиторий. Для повторной генерации нужен `flatc` версии 25.12.19; Go-библиотека FlatBuffers закреплена в `go.mod`:

```sh
./generate.sh
go test -race ./...
```

В локальном прогоне с одним установленным TCP-соединением (`ss`) режим с сериализацией до очереди дал в среднем 4,11 млн ответов/с за последние пять секунд. Режим с передачей одних ID в очередь и сериализацией в горутине записи давал 7,45 млн ответов/с; отдельный `Write` на каждый запрос — 33,7 тыс. ответов/с. Результат зависит от машины и нагрузки.

Проверка размеров `wire.BufferSize` при сборке клиента и сервера: один TCP-сокет, около шести секунд на вариант, среднее последних четырёх секунд. Этот параметр задаёт буфер записи клиента, буферы чтения и буфер ответов сервера.

| Буфер | Ответов/с |
| ---: | ---: |
| 64 КБ | 4,20 млн |
| 128 КБ | 4,13 млн |
| 256 КБ | 4,06 млн |
| 512 КБ | 4,13 млн |
| 1 МБ | 4,21 млн |
| 2 МБ | 4,17 млн |
| 64 КБ, повторный прогон | 4,35 млн |

Увеличение буфера не дало устойчивого выигрыша, поэтому значение 64 КБ сохранено.

Проверка в меньшую сторону: для каждого значения собраны клиент и сервер с изменённым только `wire.BufferSize`; настройки TCP не менялись. На локальном соединении измерялся `responses/s`, в таблице указано среднее последних четырёх полных секунд каждого прогона. Короткие прогоны длились 7 секунд, контрольные — 12 секунд. Во всех 16 прогонах `ss` показывал ровно два конца одного установленного TCP-соединения. [Посекундные измерения](benchmarks/buffer-size-smaller.jsonl).

| Буфер | 7 с, млн ответов/с | 12 с, млн ответов/с |
| ---: | ---: | ---: |
| 64 КБ | 4,25 / 4,17 / 4,33 | 4,08 / 4,10 |
| 48 КБ | 4,23 | — |
| 40 КБ | 4,23 | — |
| 32 КБ | 4,47 / 4,53 / 4,31 | 3,99 / 4,01 |
| 28 КБ | 4,31 | — |
| 24 КБ | 4,15 | — |
| 16 КБ | 4,08 | — |
| 8 КБ | 2,95 | — |

На коротких прогонах 32 КБ иногда выигрывал, но в обоих длинных прогонах его установившийся RPS был ниже 64 КБ. Уменьшение до 16 и особенно до 8 КБ снижает скорость. Устойчивого выигрыша нет, поэтому оставлен буфер 64 КБ. Значения ниже 8 КБ не проверялись: буфер чтения должен вместить максимально допустимый кадр `MaxFrameSize` (4 КБ) вместе с префиксом длины.

## Профилирование клиента через HTTP

Включите локальный сервер `net/http/pprof` при запуске клиента:

```sh
go run ./cmd/client -pprof-listen 127.0.0.1:6060 127.0.0.1 9002
```

Без `-pprof-listen` HTTP-сервер не запускается. Страница со списком профилей доступна по адресу `http://127.0.0.1:6060/debug/pprof/`. Профилирование идёт на работающем клиенте; соединение клиента с сервером остаётся одним, а запросы к pprof используют отдельное локальное HTTP-соединение. Когда pprof включён, память профилируется с шагом выборки 16 КБ; параметр `-pprof-mem-rate` задаёт другой шаг в байтах.

Сохранить CPU-профиль, профиль аллокаций и runtime trace:

```sh
mkdir -p profiles
curl -o profiles/client-http.cpu.pprof 'http://127.0.0.1:6060/debug/pprof/profile?seconds=15'
curl -o profiles/client-http.allocs.pprof 'http://127.0.0.1:6060/debug/pprof/allocs?seconds=15'
curl -o profiles/client-http.trace 'http://127.0.0.1:6060/debug/pprof/trace?seconds=5'
```

Каждая команда измеряет свой интервал после вызова; для одновременного интервала запустите первые две команды параллельно. `allocs` показывает оценку числа выделений по выборке. Посмотреть flame graph и временную шкалу GC:

```sh
go tool pprof -http=127.0.0.1:8080 profiles/client-http.cpu.pprof
go tool pprof -http=127.0.0.1:8081 -alloc_objects profiles/client-http.allocs.pprof
go run cmd/trace -http=127.0.0.1:8082 profiles/client-http.trace
```

В интерфейсе pprof откройте **Flame Graph**, а в интерфейсе trace — **View trace**. Чтобы фазы GC встречались чаще, можно отдельно запустить клиент с `GOGC=1` и снова запросить `/debug/pprof/trace`; такой запуск меняет условия измерения RPS. На этой машине команда `go tool trace` отсутствует, поэтому просмотрщик запускается из исходников Go через `go run cmd/trace`.
